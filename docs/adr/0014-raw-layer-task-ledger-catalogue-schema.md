# One raw table per source, a permanent task ledger, and the catalogue schema

The pipeline stores each source response untouched in a raw table, tracks every fetch in a task table, and parses the raw rows into the catalogue tables. Parsing can be redone from the raw layer without fetching again. The shapes below come from the probe in `docs/METRICS.md` and the sample responses.

## Decisions

**Raw layer**
- **One raw table per source.** Tenrai's is `raw_tenrai`, keyed `(mal_id, resource)`, with a `JSONB` `payload` and `fetched_at`. A refresh overwrites the row; there is no history (ADR 0004).
- **A raw row exists only for a successful fetch.** There is no `http_status` column, because the outcome of a failed fetch (404, retries exhausted) lives on the task. There is no `source` column either, because the table name is the source.
- **A multi-page Resource keeps every page in one row** (a list of pages), written once after the last page. If a page fails, nothing is stored and the task is retried from page 1. Only 1-7% of anime have more than one episodes page (ADR 0012).
- **Rejected: one generic raw table for all sources.** The sources differ in key and shape: Tenrai is keyed by MAL id, AniList by its own id, and IMDb is bulk dumps keyed by `tconst`. A generic table would need a text key and would fit IMDb badly.

**Task ledger**
- **`ingestion_task` is keyed `(mal_id, resource)`**, with no foreign key to `anime`, because tasks exist before the anime row does. Columns: `status` (`pending`, `done`, `failed`, `dead`, `gone`), `attempts`, `next_attempt_at`, `last_error`, and timestamps. `resource` also allows `characters` so that a later pass only inserts task rows.
- **Rows are never deleted.** A refresh resets the target rows to `pending` with `attempts = 0`. Discovery inserts with `ON CONFLICT DO NOTHING`.
- **The adapter's own retries (ADR 0012) happen inside one call.** A task becomes `failed` only after the adapter gives up, and `dead` after too many task-level attempts. `dead` is never retried automatically, so it can be inspected. A 404 is `gone`.
- **Our own enums** (`Resource`, `TaskStatus`) are Python `StrEnum`s stored as `VARCHAR` with explicit `CHECK` constraints. They are not native Postgres enums, which are hard to change later, and they do not use `Enum(create_constraint=True)`, because Alembic ignores those constraints on the model side and `alembic check` then reports drift.
- **Values controlled by MAL get no `CHECK`** (type, status, rating, relation name). A new MAL value must not make an upsert fail and send the task to `dead`.

**Catalogue**
- **Primary keys are MAL's own ids** and are never generated by the database.
- **`anime` holds single-valued fields.** Tags (genres, themes, demographics) share one MAL id space, so one `tag` table with `mal_id` and `name` is enough, joined by `anime_tag`. Studios are `studio` and `anime_studio`, so a studio can later carry more detail.
- **`anime_statistics_mal`** is one row per anime with the list counts and `votes_1` to `votes_10`. `anime_relation` holds only anime-to-anime edges and is keyed `(anime_id, relation, related_mal_id)`. The target has no foreign key because it may not be ingested. Manga relations (such as Adaptation) are not stored, because they are not needed for the watch order and visualisation, and `anime.source_material` already records the source. They stay in `raw_tenrai`, so they can be added later by re-parsing.
- **`episode`** is keyed `(anime_id, episode_number)`. **`review`** is keyed by the review's own `mal_id` and is fed from page 1, the 20 most helpful reviews.
- **Reviews are added, never deleted.** The parser upserts on the review's `mal_id`. A review seen again has its reaction counts updated, and one that falls off page 1 keeps its last-seen values, so the stored set grows across refreshes. `updated_at` shows when a review was last seen.
- **Scores are stored 0-10, one column per source** (`mal_score`, `anilist_score`, `imdb_score`) on both `anime` and `episode`. MAL's 0-5 episode scores are doubled, and an episode score of 0 means "no score" and is stored as null. Each pipeline's upsert writes only its own column.
- **Reviews are spoiler-free by default.** All 6,034 reviews in the probe have `is_spoiler = false`, so the server excludes spoiler and preliminary reviews unless asked. We keep the flags but do not fetch spoiler reviews: a leaked twist in LLM output is a product failure, and a second pass would cost extra calls.

**Parsing**
- **Hashes:** only `anime.synopsis_hash` is stored, because a changed synopsis triggers re-embedding (ADR 0007). A hash of the descriptive data (titles, tags, studios, relations) is computed in memory only, to measure how often child tables would change.
- **Tags:** the `tag` table is loaded into a dict once per job run. For each anime, tags missing from the dict are inserted and renamed tags are updated, so there are no per-anime tag reads. Each anime's tag and studio links are replaced in one transaction. A separate genres endpoint is not used, because genres are not per-anime and do not fit the task table.
- **Text cleaning:** strip `[Written by MAL Rewrite]` and placeholder synopses before storing or embedding. If a date is partial (a year but no full `aired_from`), store the year.
- **Trending** needs no extra storage. It is derived from recent episode scores plus the anime's percentile of members and score among Currently Airing anime. Weekly snapshots would be the proper signal, but they conflict with ADR 0004 and need their own ADR.

## Consequences

- **IMDb and AniList need their own pipelines.** Each gets its own source adapter and rate limiter (ADR 0008), its own raw table (or landing of its bulk files), parsers, and, for IMDb, the Match step (ADR 0002). Their shapes are settled after a probe like the Tenrai one. They populate `anilist_score` and `imdb_score` on `anime` and `episode`, which stay null until then.
- **`ingestion_task` is Tenrai-specific for now**, because it is keyed by `mal_id`. How the other sources track their fetches is decided with their pipelines.
- **Several pipelines write the same `anime` and `episode` rows**, so each upsert must update only the columns it owns.
- **Characters** get their own pipeline later, with descriptions fetched per character. `anime.background` is kept as context for LLM answers about why a show is notable.
- **Reviews accumulate**, so ranking all stored reviews by `reaction_overall` is approximate: reviews that left page 1 keep stale counts, and reviews MAL deleted stay in the table. The reviewer's `username` and its URL are stored. They are public MAL profile data, so they may appear in logs (for example the response logged when a task fails). Do not send them to an LLM. The review `tags` field is dropped from the table, but it stays in `raw_tenrai`.
- **Tests:** SQL here is verified with the real-Postgres exception in ADR 0006, not mocks.

## Revisit if

- A second process has to write the tag table, because the in-memory dict would go stale.
- A new MAL type, status or relation name breaks a parser assumption.
- Analysis needs spoiler reviews, the dropped review tags, or per-source score history.
